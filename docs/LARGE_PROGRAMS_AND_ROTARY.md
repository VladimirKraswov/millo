# Большие программы и ось A

Срез от 6 сентября 2026. Изменения относятся к выполнению готового G-code,
а не к генерации четырёхосевого CAM или расчёту столкновений.

## Большие файлы

Файл открывается обычной кнопкой загрузки. Rust хранит неизменяемую версию
исходника и полный результат разбора. Проверка, разрешение и sender обращаются
к этой версии по ID, не передают заново миллионы строк через Tauri и не копируют
всю геометрию между командами. Исходник остаётся доступен редактору.

| Ресурс | Граница |
| --- | --- |
| Исходный UTF-8 файл | 64 MiB |
| Строки исходника | 2 000 000 |
| Длина одной исходной строки | 16 KiB; отправляемый блок дополнительно ограничен GRBL/RX |
| Полная геометрия ядра | 4 000 000 точек |
| Диагностика ядра | 10 000 сообщений; превышение отклоняет разбор |
| Кэш разобранных документов | Не более 4 версий и 768 MiB расчётного объёма данных |
| Обзорная траектория UI | Не более 50 000 точек |
| Страница таблицы | 512 строк, переход по номеру к любой строке |
| Страница редактирования | 5 000 строк; подсветка только видимой части |
| Undo/redo | До 200 изменений в пределах 8 MiB дельт |

Это совместные ограничения, а не обещание, что любой файл размером 64 MiB
поместится независимо от его геометрии. Переполнение ресурсов отклоняется
явно. Старое задание не заменяется усечённым результатом. Кэш оценивает данные
документов, не общую память процесса: исходник JS, worker, sender, WebGL и
аллокатор тоже расходуют память. Разбор и план пока материализуются в памяти,
это не безлимитный дисковый streaming parser.

У больших траекторий появляется пометка «Обзорная траектория». Пропущенные
движения не соединяются выдуманными отрезками. Границы и статистика берутся из
полного разбора; выбранная строка отдельно получает свою геометрию. Проверка
и выполнение всегда используют все строки, не обзорную картинку.

Редактор сохраняет полный исходник. «Обработанная копия» экспортируется ядром
со всеми страницами и текущим Block Delete. При вытеснении старой версии из
кэша чтение/подготовка автоматически повторно открывает сохранённый исходник
с прежними настройками. Повторяется только явный отказ до отправки команды;
ошибка serial, истёкшее разрешение или неопределённый результат запуска не
приводят к автоматической повторной отправке.

Если одно изменение превышает бюджет undo, история очищается с видимым
сообщением. Само изменение не обрезается. Перемещение курсора, копирование,
вставка, сохранение и применение относятся к глобальному документу, а не к
текущей странице.

## Четыре оси

Обычная GRBL 1.1 трёхосевая. Выбор A в профиле не добавляет её в прошивку.
Для выполнения необходимы текущие координаты XYZA, профиль с поворотной осью
и подтверждённый угловой контракт контроллера:

- grblHAL: однозначный firmware report, XYZA и `$376` с установленным битом A
  (публичная маска `1`, а не `8`). Millo не меняет эту настройку самостоятельно.
- FluidNC: версия с идентификатором FluidNC и подтверждённые четыре координаты.
- MilloVirtual: явный виртуальный четырёхосевой режим, не обычный XYZ mock.

Точные признаки, первичные источники и ограничения каждой прошивки:
[ROTARY_CONTROLLER_COMPATIBILITY](ROTARY_CONTROLLER_COMPATIBILITY.md).

Поддержаны G0/G1 XYZ+A и A-only, G90/G91, G20/G21, G93/G94, неограниченный
модулем 360 угол (например A720). A всегда задаётся в градусах; G20 меняет XYZ,
но не умножает A на 25.4. Дуги с A разбираются и могут проверяться/выполняться
на поддерживающем их контроллере; виртуальный контроллер их явно отвергает.
Для G93 нужен положительный F в каждом блоке рабочего движения.

G94 с поворотом зависит от кинематики и прошивки. Его оценка времени помечается
неполной, а не выдаётся за точный прогноз. G93 задаёт номинальное время блока,
но реальные ограничения скорости и ускорения всё равно действуют.

Preview показывает **проекцию XYZ**, диапазон и путь A, углы выбранного
сегмента, текущее A в градусах и выделяемые маркеры A-only. Это не модель
вращающейся заготовки, не проверка столкновений и не симуляция снятого материала.
Вращение шпинделя и поворот заготовки A не смешиваются.

Zero A доступен отдельно и выполняет проверяемый `G10 L20 Pn A0`; общий Zero
XYZ не меняет A. Автоматический «вернуть A в ноль» не добавлен: положительный Z
не доказывает, что заготовка, патрон и крепёж смогут свободно повернуться.

## Запуск и восстановление

Четырёхосевые программы проходят тот же sender: ограниченный RX, точные ACK,
Check, одноразовое разрешение, Hold/Reset, управляемую M6 и журнал восстановления.
Перед запуском оператор проверяет не только XYZ-ноль, но и индекс A и зазор
для всей вращающейся заготовки. После долгой подготовки/записи recovery снова
проверяются Idle, сессия и неизменность координат до допуска отправки.
Для программы с A Check обязателен и в «Проверке движения». На паузе M6
фиксируются индекс/смещение A и активный WCS: новый Z-ноль допускается,
изменённый ноль или угол A блокирует продолжение до восстановления привязки.

Запуск с выбранной строки требует подтверждения начального A исходной
программы и свободного поворота на Safe Z. Подход состоит из отдельных движений:
подъём Z, восстановление A, подход XY, подход Z, затем оставшаяся программа.
Неизвестные координаты нельзя заменить нулями из preview: если опорное XYZ/A
невозможно восстановить, подготовка отклоняется. Оставшийся код требует Check.

При восстановлении собственного прерванного задания A и WCO A сверяются с
сохранёнными данными. Reconnect/reset не означают, что механическая позиция
восстановлена. Требуется физически восстановить базирование/индекс и подтвердить
неподвижность заготовки; автоматического продолжения после питания нет.

Recovery schema 2 хранит небольшой JSON состояния и неизменяемый исходник
в `<recovery-file>.sources/<SHA-256>.nc`. Сначала исходник синхронизируется на
диск, затем публикуется ссылка в атомарном JSON. Каждый checkpoint не переписывает
весь G-code. Старые записи со встроенным исходником читаются и мигрируют;
проверяются размер, digest и резервная копия. Sidecar-файлы пока не удаляются
автоматически, чтобы не разрушить rollback/backup. При резервном копировании
нужно сохранять JSON, его backup и всю соседнюю `.sources` директорию вместе.

## Ограничения преобразований

- Карта высот XY+Z не применяется к программам с A. Для вращающейся заготовки
  нужен другой геометрический контракт, не обычная плоская сетка.
- Коррекция глубины поддержана для проверяемых линейных/быстрых G21/G90/G94
  блоков с A. Неподдержанные дуги, G93, относительные и дюймовые преобразования
  отклоняются, а не превращаются незаметно в XYZ.
- Профиль и программные границы не доказывают свободный оборот, допустимость
  кабелей или отсутствие столкновения. Аппаратная квалификация grblHAL/FluidNC
  и конкретной механики остаётся отдельной работой.

## Воспроизводимые проверки

```sh
npm test
npm run build
npm run lint:rust
npm run test:workflow
cargo run --release -p millo-sender --example large_program -- 1000000
cargo test --release -p millo-desktop --lib million_line_document_benchmark -- --ignored --nocapture
cargo test --release -p millo-command --test rotary_program million_line_rotary_actor_benchmark -- --ignored --nocapture
cargo run -p millo-virtual-controller -- --rotary
```

Замер полного in-memory sender на этой машине: 1 000 000 движений,
21 800 020 байт исходника, 1 000 005 отправляемых блоков; parse 1.16 s,
plan 0.97 s, dispatch/ACK 1.31 s; peak RSS 734 707 712 байт (около 701 MiB).
Это release-бенчмарк с мгновенными тестовыми ACK, а не скорость реального
станка и не измерение аппаратной задержки Hold.

Отдельный native-тест с миллионом строк: расчётный объём документа
364 212 965 байт, исходник 11 000 034 байт, JSON обзорного UI 1 140 321 байт;
разбор 1.69 s, вместе с подготовкой UI 1.72 s. Проверена точная предпоследняя
строка с A90 и последняя M2, не только первые 512 строк.

Полный command-actor тест с миллионом строк XYZ+A на нагруженном компьютере
занял 263.45 s: Check 166.20 s, preflight 15.26 s, authorization 24.31 s,
prepare 33.19 s. Во время отправки тестовый Hold обработан за 0.058 ms,
Reset за 0.404 ms. Это in-memory transport, не serial и не механическое
торможение. CPU-подготовка такого объёма пока дорогая: эти цифры нельзя
подменять быстрым изолированным замером parser. Она допускается только в Idle,
а непосредственно перед отправкой привязка проверяется повторно.

Тесты проверяют ось A и единицы, G93, ошибочные/несовместимые контроллеры,
преобразования, restart/recovery, точную последнюю страницу, полный экспорт,
вытеснение кэша, stale UI responses, миллион строк редактора, desktop/mobile
layout и пиксели WebGL. Физические команды в этом срезе не выполнялись.
